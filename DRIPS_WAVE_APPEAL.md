## Acknowledgement of Previous Issues

We acknowledge the following issues existed in the original submission:

### 1. Manufactured commit history (Critical)

`generate-commits.js` was present in the repository and was used to generate
approximately 115 backdated commits with autogenerated messages intended to
inflate the apparent development history. This was wrong. The file has been
excluded from the repository via `.gitignore` and is documented in `AUDIT.md`.
The commit history created by that script does not reflect genuine development
effort and should be disregarded by reviewers.

### 2. Simulated blockchain transactions (Critical)

The original `stellar.service.ts` returned fake transaction IDs generated with
`Math.random()` and `Date.now()` for all escrow and payment operations. No
actual on-chain transactions were created. This has been fully rewritten: the
service now uses real Stellar SDK operations (Claimable Balances, Payment
operations) against the Testnet Horizon API, and throws a descriptive error
rather than fabricating data when credentials are missing.

### 3. Disabled authentication (Critical)

The JWT middleware was commented out with a TODO note, leaving all API endpoints
publicly accessible without any token verification. This has been corrected: the
middleware now calls `request.jwtVerify()` and the server refuses to start if
`JWT_SECRET` is not set in the environment.

### 4. Real credentials in a public file (Critical)

`backend/.env.example` contained a real Supabase project URL and publishable
key. These have been replaced with clearly labelled placeholder strings and
instructions for obtaining real values.

## Stellar / Soroban Alignment

### Claimable Balance escrow

The Claimable Balance mechanism is the right fit for crop trade escrow on Stellar
because it does not require the platform to hold private keys on behalf of
participants. The seller and buyer each hold their own Freighter wallet. The
platform account creates the balance; the seller claims it on confirmed delivery;
the buyer can reclaim it before the deadline if the trade is cancelled.

### Soroban escrow contract

For trades requiring more complex on-chain logic — time-locked refunds, inspector
roles, partial releases — the Soroban contract in `contracts/escrow/` provides a
typed state machine (`PENDING → FUNDED → RELEASED | REFUNDED`) with two
comprehensive tests. It needs to be compiled (`cargo build
--target wasm32-unknown-unknown --release`) and deployed via the Stellar CLI to
produce a contract ID before it can be called from the backend.

### What we still need from reviewers

1. **A funded Testnet account** — to demonstrate live Claimable Balance creation
   during a review call, we need the platform keypair to be funded. We can use
   Friendbot for this.
2. **Rust toolchain availability** — to compile the Soroban contract in CI, we
   need the GitHub Actions runner to have `rustup` and the `wasm32-unknown-unknown`
   target available. This is straightforward to add to the workflow.
